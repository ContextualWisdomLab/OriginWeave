# ADR 0012: Preserve HTTP/1.1 reason phrases as bounded diagnostic bytes

- Status: Proposed
- Date: 2026-08-09
- Supersedes: historical unmerged `docs/adr/0008-http-reason-phrase-diagnostics.md` from PR #11

## Context

RFC 9112 defines an HTTP/1.1 status line as `HTTP-version SP status-code SP [ reason-phrase ]`. The second separating space is mandatory even when the optional reason phrase is empty. The reason phrase can contain `obs-text`, so a conforming value is not necessarily UTF-8. RFC 9112 also makes clear that clients should ignore its content for HTTP semantics because it is potentially obsolete and unreliable.

OriginWeave needs diagnostics that preserve what an authenticated peer actually sent without allowing attacker-controlled diagnostic text to become protocol authority, policy input, audit metadata, or a lossy Unicode string.

## Decision drivers

- Preserve exact validated wire diagnostics for troubleshooting.
- Keep HTTP status semantics exclusively in the numeric status code.
- Avoid lossy UTF-8 conversion of valid `obs-text`.
- Prevent remote reason text from entering durable evidence or authorization decisions.
- Reuse the existing status-line byte bound rather than create another allocation surface.

## Assumptions and authority boundaries

The reason phrase is accepted only after the status line has crossed the bounded strict HTTP/1.1 parser. It is peer-controlled diagnostic data. It does not grant authority and is never interpreted as framing, redirect, MIME, integrity, policy, approval, business outcome, or provenance content.

## Options considered

### Discard reason phrases

Rejected because exact peer diagnostics are valuable for debugging and standards conformance, especially when diagnosing unusual servers.

### Decode as UTF-8 `String`

Rejected because RFC 9112 permits `obs-text`; conversion would either reject valid status lines or silently replace bytes.

### Copy into `HttpExchangeEvidence`

Rejected because that would durably retain arbitrary attacker-controlled bytes with no authority or audit requirement.

## Decision

`AuthenticatedHttpResponse` retains the exact final reason-phrase octets as a bounded `Vec<u8>` after complete status-line syntax validation.

The public response exposes the bytes through `reason_phrase()` and preserves them in `into_parts()`. The value is bounded by the existing status-line budget. The status code alone drives HTTP semantics.

The reason phrase is excluded from `HttpExchangeEvidence`, generic credential-free provenance, policy decisions, logs generated by the HTTP authority, and all downstream authority calculations. Consumers that choose to display it own escaping and presentation safety.

The parser accepts an empty reason phrase when the mandatory separating space is present and accepts valid `obs-text` bytes without UTF-8 conversion. A status line that omits the required second space remains invalid.

## Consequences

### Positive

- Operator diagnostics preserve the peer's exact bounded bytes.
- Standards-valid non-UTF-8 reason phrases remain interoperable.
- Diagnostic text cannot silently become HTTP or security authority.
- Durable evidence remains free of unnecessary attacker-controlled strings.

### Negative

- Callers that display the value must explicitly escape arbitrary bytes.
- The public response has a second byte vector in addition to content, though it is already bounded by the status-line budget.

## Failure and degraded behavior

Malformed status syntax is rejected before any reason phrase is exposed. A reason phrase containing bytes outside the RFC 9112 accepted class causes the status line to fail closed. No lossy replacement or partial diagnostic value is returned.

## Security / privacy / governance impact

This decision limits persistence and semantic use of server-controlled diagnostic text. It reduces log-injection and durable-untrusted-metadata risk while retaining bounded troubleshooting value. It does not change authentication, authorization, privacy, or HTTP framing authority.

## Tests and acceptance evidence

Acceptance requires tests that:

- preserve `b"OK"` exactly;
- preserve an empty phrase after the mandatory second space;
- preserve valid `obs-text`, including a byte such as `0xff`;
- reject a status line missing the mandatory second space;
- prove through an authenticated loopback TLS exchange that the final bytes reach `reason_phrase()` and `into_parts()` unchanged;
- keep the bytes absent from `HttpExchangeEvidence`;
- pass current exact-head formatting, tests, Clippy, rustdoc, exact coverage, Security Scan, SAST, current review cleanup, and branch policy.

## Migration and rollback

The accessor is additive to the reconstructed HTTP response API. Rollback removes the diagnostic accessor while leaving numeric status, framing, and evidence semantics unchanged. A future migration to a richer diagnostic representation must remain byte-preserving or explicitly document any interoperability loss.

## Open follow-ups

- Ensure operator/UI surfaces escape diagnostic bytes before display.
- Keep reason phrase out of generic evidence schemas as the protocol evolves.

## Supersession / reversal conditions

Supersede this ADR if OriginWeave adopts another HTTP parser/protocol representation that either cannot expose HTTP/1.1 reason phrases or provides a stronger byte-preserving diagnostic envelope with the same non-authoritative boundary.
