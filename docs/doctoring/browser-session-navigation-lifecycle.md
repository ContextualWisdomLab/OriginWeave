# Browser Session navigation lifecycle authority

Status: acceptance design for the active Browser Session stack; not protected-main runtime behavior.

## Standards boundary

Fresh verification on 14 September 2026 shows that the canonical W3C Technical Report page identifies *WebDriver BiDi* as a Working Draft published on 24 August 2026 and links the immutable dated publication `https://www.w3.org/TR/2026/WD-webdriver-bidi-20260824/`. It identifies the 18 August 2026 Working Draft as the previous published version and `https://w3c.github.io/webdriver-bidi/` as the Editor's Draft. The repository's separate 9 September / 3 September publication claims are not reproduced by the canonical W3C publication surface and therefore are not treated as authoritative evidence in this acceptance document.

Publication freshness is not runtime compatibility. This branch does not infer a runtime repin from the 24 August publication. The canonical #317 owner must repair `docs/traceability/webdriver-bidi-publication-current.md`, its currentness contract, and related ADR evidence so that any runtime-qualified revision is backed by reproducible compatibility evidence. Until that repair lands, this document records current W3C publication semantics only and does not independently validate the repository's previous 3 September runtime claim.

The 24 August publication defines `browsingContext.Navigation` as a per-navigation identifier and carries it through `NavigationInfo` with the browsing context, timestamp, URL, and user context. It defines separate navigation lifecycle events including `navigationStarted`, `fragmentNavigated`, `domContentLoaded`, `load`, `downloadWillBegin`, `downloadEnd`, `navigationAborted`, `navigationCommitted`, and `navigationFailed`. Those protocol identifiers and events are evidence available to a BiDi adapter. They are not OriginWeave policy authority.

The same publication's `await a navigation` algorithm distinguishes commitment from completion. After a normal `navigationStarted`, the navigation status is still pending; the command can separately wait for `committed`, `domContentLoaded`, or `load`, while a fragment-only navigation returns through `fragmentNavigated` with complete status. A `navigationCommitted` event therefore cannot be treated as terminal completion merely because a BiDi command wait condition may return at commitment. OriginWeave must keep mutation authority revoked while the navigation remains capable of reaching a later `navigationAborted`, `navigationFailed`, completion, or download-start liveness outcome.

The algorithm also includes `"download started"` in the post-start wait set. `browsingContext.downloadWillBegin` carries navigation/context correlation in `BaseNavigationInfo` and resumes that navigation waiter with `"download started"`. This is a Browser Session navigation-liveness boundary, not evidence that the subsequent file download has completed or passed policy. Without a typed download-start transition, a navigation that becomes a download can leave presentation mutation authority stranded because it will not necessarily reach the ordinary document `load` path. Download persistence, scanning, egress, quarantine, and `downloadEnd` lifecycle remain outside Browser Session authority.

## Acceptance decision

The active #316/#317/#318 stack is still proposed integration work. The intended boundary is:

- #316 must use the protocol navigation identifier to distinguish delivery replay from a genuinely later navigation and correlate lifecycle evidence. It must not expose that identifier as Browser Session capability authority. Matching `navigationCommitted` is non-authorizing progress only; it must not be mapped to positive settlement.
- #317 must validate non-authorizing Browser Session incarnation, browsing-context, and context-epoch provenance before invalidating presentation mutation authority and issuing an opaque aggregate-owned pending witness. A matching commit-progress observation must validate the same aggregate-issued witness without consuming it, spending a presentation epoch, or enabling re-establishment.
- Positive settlement is an OriginWeave mapping from qualified matching completion evidence: `browsingContext.load` for a document navigation or `fragmentNavigated` for the same-document fragment path that the W3C algorithm reports complete. `navigationCommitted` and `domContentLoaded` are progress evidence only. `navigationAborted` and `navigationFailed` map to distinct typed negative terminal outcomes. No protocol event implicitly restores presentation authority.
- A matching `browsingContext.downloadWillBegin` closes the current navigation's pending liveness boundary through a separate witness-bound Browser Session transition. It is neither document-completion evidence nor a negative termination. It must not spend a presentation epoch or perform browser I/O, and retained pre-navigation presentation authority stays revoked. Only one later explicit `reestablish_presentation_authority` may mint fresh presentation authority. `downloadEnd` belongs to the subsequent download lifecycle and must not mint Browser Session authority.
- Once Browser Session accepts matching `downloadWillBegin`, that exact aggregate-issued navigation witness is consumed for authority transitions. Later `navigationCommitted`, complete-positive, `navigationAborted`, or `navigationFailed` evidence carrying the same consumed witness must fail `AuthorityMismatch` before lifecycle, recovery, authority, epoch, or adapter-I/O mutation. Before explicit re-establishment, such replay must preserve the download-derived single re-establishment opportunity; after re-establishment, it must leave the newly minted authority executable and must not create a second opportunity. This is an OriginWeave exactly-once authority decision over the W3C liveness result, not a claim that the protocol forbids later event delivery.
- A matching `navigationAborted` that arrives after `navigationCommitted` remains an admissible terminal outcome for the same pending witness. A matching `navigationFailed` after commit is independently admissible. Commitment must not consume the witness or turn either later negative outcome into a conflicting replay. Likewise, a matching complete positive settlement after commitment consumes the same witness exactly once.
- A later qualified navigation start for the same live context supersedes an earlier pending witness without spending a presentation epoch. It is also admissible after the preceding navigation reached either a positive or negative terminal outcome when presentation authority has not yet been explicitly re-established. In both cases, delayed positive or negative terminal evidence for the earlier navigation must fail closed while the newer navigation remains pending. If the earlier navigation closed through `downloadWillBegin` and left an unused re-establishment opportunity, the later start must discard that opportunity before installing the new pending witness while keeping the earlier witness consumed. `navigationCommitted`, complete-positive, `navigationAborted`, and `navigationFailed` replay from that consumed witness must remain observationally non-mutating while the newer navigation is pending: aggregate lifecycle state, recovery evidence, revoked retained authority, adapter-I/O count, and the aggregate presentation-epoch sequence stay unchanged.
- Navigation lifecycle state is scoped to the exact owned browsing context, not to one aggregate-wide pending/terminal flag. A valid terminal-derived re-establishment opportunity for one context may coexist with a later pending navigation in a sibling context; that sibling start or terminal transition must not erase the first context's opportunity, and neither navigation observation may spend a presentation epoch.
- The same context-local rule applies to download-derived re-establishment eligibility. `downloadWillBegin(A)` may close A's navigation liveness and leave one unused explicit re-establishment opportunity while sibling context B starts a separate navigation. B's start must not erase A's opportunity, and A's already-consumed download witness must remain non-authorizing replay rather than being remapped into B. A may re-establish independently while B remains pending; B stays fail-closed until its own qualified closing evidence, and each successful re-establishment receives the next aggregate-issued epoch without sibling observations spending one.
- Proven destruction is context-local as well. Destroying one owned context after its terminal outcome consumes that context's ownership and terminal-derived re-establishment opportunity, but must not clear, settle, or replace a sibling context's pending navigation. The surviving sibling must remain fail-closed until its own terminal outcome and continue the aggregate-wide presentation-epoch sequence without the destruction operation spending an epoch.
- Context-local destruction also applies while both contexts are navigation-pending. Destroying pending context A consumes A ownership and A's pending witness, so delayed positive or negative terminal evidence for A must return `ContextNotOwned`; it must not clear sibling B's pending navigation, reactivate B's retained pre-navigation authority, or spend an aggregate presentation epoch. Successful destruction and rejected `Aborted`/`Failed` replay must leave the aggregate `Active` and preserve recovery evidence exactly; they must not synthesize a recovery condition. B may reach its own terminal outcome and only then receive the next aggregate-issued presentation epoch.
- Raw browsing-context identifiers are not ownership generations. After proven destruction, a later accepted disposable context may reuse the same raw `BrowsingContextId`, but it must carry a newer aggregate-issued `BrowserContextEpoch`. Navigation witnesses and presentation authority from the destroyed generation must fail closed against the recreated generation before adapter I/O. Stale positive settlement, `Aborted`, or `Failed` evidence must not terminate the recreated context's current pending navigation, and raw-id equality must never revive the destroyed generation's authority.
- Terminal-derived re-establishment eligibility is generation-bound under the same ABA rule. If an ownership generation reaches positive settlement, `Aborted`, or `Failed`, is then proven destroyed, and a fresh ownership generation reuses the same raw browsing-context id, the fresh generation must not inherit the destroyed generation's unused re-establishment opportunity. A raw-id-only re-establishment attempt must fail closed without adapter I/O, recovery mutation, or aggregate-epoch consumption while preserving the recreated generation's current presentation authority. Only a terminal transition produced by the recreated generation may enable its next re-establishment.
- A rejected later navigation observation must be non-mutating. If incarnation, browsing-context, or context-epoch provenance is stale or belongs to another owned context, rejection must occur before adapter I/O and before replacing a valid terminal-derived re-establishment opportunity. Invalid browser evidence must not become a denial-of-service primitive against the last qualified terminal transition.
- Rejected terminal or progress evidence must also be non-mutating after a valid terminal/liveness transition. A stale or prior-incarnation settlement, termination, or commit-progress witness must fail before adapter I/O and must not consume, replace, or otherwise invalidate the current aggregate's one valid re-establishment opportunity or already-minted current authority.
- Pending witnesses must die on aggregate trust loss or proven loss of the exact context ownership, and terminal assignment must be exactly once across complete-positive and negative outcomes. Re-establishment of presentation authority is explicit and is permitted only after the current pending navigation reaches a valid terminal or download-start liveness outcome; commitment alone is insufficient.
- Each qualified navigation-closing transition permits at most one explicit presentation-authority re-establishment. Once that re-establishment succeeds, a duplicate re-establishment attempt without a newer navigation must fail closed, must not spend another aggregate epoch, and must leave the current authority intact. Ordinary epoch rotation remains a separate established-context operation and is not a substitute for navigation re-establishment.
- Terminal-derived re-establishment eligibility is subordinate to exact live context ownership. If the bound owner proves context destruction after terminal navigation evidence but before re-establishment, destruction consumes the ownership and the pending re-establishment opportunity with it; the destroyed context must not be resurrected from an otherwise valid prior terminal transition.
- Terminal-derived re-establishment eligibility is also subordinate to aggregate trust. If transport trust is lost or lifecycle cleanup moves the aggregate to `RecoveryRequired` after terminal navigation evidence but before re-establishment, the aggregate-state gate wins: re-establishment must return `SessionNotActive`, perform no adapter I/O, and preserve the exact transport or recovery evidence rather than using the earlier terminal transition to resurrect mutation authority.

This design deliberately keeps WebDriver BiDi as an adapter contract. Browser Session remains the deterministic authority boundary, and command acknowledgement, `navigationCommitted`, or any other progress event is not a browser-observed success post-condition. Issue #320 tracks the navigation-to-download liveness slice without transferring download-file ownership into Browser Session.

## Evidence still required

The current #318 branch supplies hostile contract tests, not production implementation or browser acceptance. A releasable path still requires #317 production state-machine repair, exact-head repository contracts, canonical rustfmt, locked tests, strict Clippy, warning-denying rustdoc, exact function/line/region/branch coverage, non-destructive #316 adoption, and real runtime-qualified Chromium evidence for each of these paths: start → invalidation → commit-progress-without-reestablishment → matching load/fragment completion → explicit re-establishment; start → invalidation → commit-progress-without-reestablishment → matching `navigationAborted` → explicit re-establishment; start → invalidation → commit-progress-without-reestablishment → matching `navigationFailed` → explicit re-establishment; and start → invalidation → matching `downloadWillBegin` → old authority remains rejected → delayed `navigationCommitted`/complete-positive/`navigationAborted`/`navigationFailed` replay remains non-mutating before and after exactly-one explicit re-establishment while download file lifecycle remains separately governed. The browser suite must also cover replay, overlapping navigation, terminal-then-new-start, cross-context terminal-then-sibling-start coexistence, download-close-then-sibling-start coexistence, terminal-context-destruction while a sibling remains pending, pending-context-destruction while a sibling remains pending, destroy-then-recreate raw-context ABA reuse, terminal-then-destroy-then-recreate re-establishment ABA reuse, invalid-later-navigation preservation, invalid-terminal preservation, terminal-then-context-destruction, terminal-then-aggregate-trust-loss, duplicate re-establishment, crash/transport-loss, and cleanup cases.
